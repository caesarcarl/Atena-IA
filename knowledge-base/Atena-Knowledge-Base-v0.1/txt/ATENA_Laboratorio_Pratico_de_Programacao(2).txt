Como usar este livro
Este livro é deliberadamente diferente de um manual teórico. Ele foi escrito como uma sequência de
sessões práticas de bancada: você lê o objetivo, executa comandos no Linux Mint, abre os arquivos
no Geany, compila, testa, observa o resultado e só então avança. Cada conceito de C aparece
quando passa a ser necessário para a Atena. Não há uma etapa de “estudar C inteiro” antes de
programar a IA.
A meta não é construir um modelo de linguagem do zero. A meta é programar a plataforma Atena: o
Core, os contratos, os providers, a política de privacidade, a memória, o RAG, as ferramentas, o
roteamento, o serviço de usuário e a integração com o Athenas OS. O modelo GGUF é um motor
cognitivo substituível dentro dessa plataforma.
REGRA DE BANCADA: Execute os laboratórios em ordem. Quando um checkpoint não passar, não
“compense” o erro copiando comandos adiante. Corrija a camada atual; as próximas dependem
dela.

Laboratório 1 - Preparar o Linux Mint
OBJETIVO PRÁTICO: Sair deste laboratório com GCC, CMake, Git, GDB, Geany e bibliotecas de
desenvolvimento instaladas e verificadas.
Você não instala “a linguagem C”. C é uma linguagem. O que instalamos é uma cadeia de
ferramentas capaz de transformar arquivos de texto .c em código de máquina executável pelo
processador. No Mint, a rota mais simples é o APT.
TERMINAL
  sudo apt update
  sudo apt install -y build-essential cmake git gdb pkg-config ninja-build geany geany-plugins
  libjson-c-dev libsqlite3-dev libcurl4-openssl-dev

O metapacote build-essential traz o compilador GCC, o linker, make e os headers fundamentais da
libc. CMake descreve o build; Git registra a história; GDB depura; pkg-config localiza bibliotecas;
json-c, SQLite e libcurl serão usados mais à frente.

C — CORE/REQUEST.C
  #include "atena/request.h"
  #include <string.h>
  #define ATENA_MAX_USER_TEXT_BYTES (64u * 1024u)

  AtenaStatus atena_request_validate(const AtenaRequest *request) {
      if (request == NULL || request->session_id == NULL || request->user_text == NULL)
          return ATENA_ERR_INVALID;
      if (request->session_id[0] == '\0' || request->user_text[0] == '\0')
          return ATENA_ERR_INVALID;
      if (strlen(request->user_text) > ATENA_MAX_USER_TEXT_BYTES)
          return ATENA_ERR_INVALID;
      if (request->privacy < ATENA_PRIVACY_PUBLIC || request->privacy > ATENA_PRIVACY_SECRET)
          return ATENA_ERR_INVALID;
      return ATENA_OK;
  }


O SALTO ARQUITETURAL: Uma string diz “explique ponteiros”. Um request diz: texto, sessão,
privacidade, rede permitida ou não, tools permitidas ou não e capacidades necessárias. É isso que
permite política verificável fora do LLM.


Laboratório 8 - Buffer e ownership sem magia
OBJETIVO PRÁTICO: Aprender malloc, free e ciclo de vida dentro de um tipo que será útil para
respostas HTTP e JSON.
C — INCLUDE/ATENA/BUFFER.H
  #ifndef ATENA_BUFFER_H
  #define ATENA_BUFFER_H
  #include <stddef.h>
  #include "atena/status.h"

  typedef struct {
      char *data;
      size_t length;
      size_t capacity;
  } AtenaBuffer;

  AtenaStatus atena_buffer_init(AtenaBuffer *b, size_t initial);
  AtenaStatus atena_buffer_append(AtenaBuffer *b, const char *data, size_t length);
  void atena_buffer_deinit(AtenaBuffer *b);
  #endif


C — CORE/BUFFER.C (INÍCIO)
  #include "atena/buffer.h"
  #include <stdlib.h>
  #include <string.h>

  AtenaStatus atena_buffer_init(AtenaBuffer *b, size_t initial) {
      if (!b || initial == 0) return ATENA_ERR_INVALID;
      b->data = malloc(initial);
      if (!b->data) return ATENA_ERR_NOMEM;
      b->data[0] = '\0'; b->length = 0; b->capacity = initial;
      return ATENA_OK;
  }

  void atena_buffer_deinit(AtenaBuffer *b) {
      if (!b) return;
      free(b->data); b->data = NULL; b->length = b->capacity = 0;
  }

Ownership responde quem cria, quem pode usar e quem libera. Para cada atena_buffer_init bem-
sucedido, deve existir um atena_buffer_deinit visível no caminho de saída. Essa disciplina reduz
leaks, double free e use-after-free.
REGRA DE REALLOC: Nunca sobrescreva o ponteiro original com realloc antes de saber que a
operação funcionou. Guarde o retorno em um ponteiro temporário e só depois atualize o objeto.

Laboratório 11 - Provider Mock: testar arquitetura
antes da IA real
OBJETIVO PRÁTICO: Emitir eventos previsíveis sem modelo, rede, GPU ou downloads.
C — PROVIDERS/MOCK.C (NÚCLEO)
  #include "atena/mock_provider.h"
  #include <stdlib.h>

  static AtenaStatus mock_generate(AtenaProvider *self, const AtenaRequest *request,
                                   AtenaEventCallback callback, void *user_data) {
      if (!self || !callback) return ATENA_ERR_INVALID;
      AtenaStatus s = atena_request_validate(request);
      if (s != ATENA_OK) return s;

      AtenaEvent e1 = { ATENA_EVENT_TEXT_DELTA, request->id,
          "{\"text\":\"Atena mock: recebi sua solicitacao.\"}" };
      s = callback(&e1, user_data);
      if (s != ATENA_OK) return s;

      AtenaEvent done = { ATENA_EVENT_DONE, request->id, "{\"status\":\"ok\"}" };
      return callback(&done, user_data);
  }


O mock não é “tempo perdido”. Ele torna os testes determinísticos. Se a CLI, os requests e os
eventos funcionam com Mock e quebram com llama-server, você já reduziu a superfície do problema
ao provider real ou ao transporte.

  AtenaStatus atena_policy_evaluate(const AtenaRequest *r, AtenaPolicyDecision *out) {
      if (!r || !out) return ATENA_ERR_INVALID;
      out->cloud_allowed = r->allow_network;
      out->tools_allowed = r->allow_tools;
      out->confirmation_required = false;

      if (r->privacy == ATENA_PRIVACY_PRIVATE || r->privacy == ATENA_PRIVACY_SECRET)
          out->cloud_allowed = false;
      if (r->privacy == ATENA_PRIVACY_SENSITIVE && r->allow_network)
          out->confirmation_required = true;
      return ATENA_OK;
  }


ORDEM NÃO NEGOCIÁVEL: Privacidade e autorização são avaliadas antes de qualidade, custo ou
velocidade. Um provider remoto “melhor” não entra no conjunto de candidatos quando a política
exige processamento local.
Crie testes de tabela: PUBLIC/NORMAL podem usar cloud quando allow_network=true;
PRIVATE/SECRET nunca; SENSITIVE exige confirmação quando a saída de dados é necessária. Esses
testes são mais importantes do que perguntar a um LLM se ele “seria seguro”.

peer. Depois, quando o contrato estiver estável, D-Bus pode expor métodos semânticos como Ask,
Cancel, ListModels e InvokeSkill.

Apêndice E - Regras de segurança que não podem
desaparecer
   O Core roda como usuário; root só existe em helper mínimo durante ação específica.
   Nunca execute texto de shell produzido pelo modelo.
   Privacidade e autorização são aplicadas antes do roteamento de provider/modelo.
   Segredos não entram em prompt, log, screenshot, linha de comando ou repositório.
   Documentos RAG são dados não confiáveis; podem conter prompt injection.
   Tools possuem nome, schema, risco, autorização e implementação conhecida.
   Rede remota é opt-in conforme modo e classe de privacidade.
   Cancelamento, limite de bytes, timeout e número máximo de passos são parte dos contratos.
   Migrações de banco são versionadas e testadas; configuração e memória são
    exportáveis/limpáveis.
   “Compilou na arquitetura” não é sinônimo de “suporte publicado”.

Arquitetura-base: “ATENA - Engenharia de uma Inteligência Artificial Nativa para Linux”, Projeto
Odisseia | Athenas OS, edição 0.1, agosto de 2026. Este livro prático reorganiza essa arquitetura em
