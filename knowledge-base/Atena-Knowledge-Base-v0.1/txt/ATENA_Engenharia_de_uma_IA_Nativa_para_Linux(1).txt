Nota editorial e estado do projeto
Este livro descreve como construir a plataforma Atena e integra-la ao Athenas OS. Ele nao afirma
que os componentes propostos ja estejam implementados. Toda afirmacao de estado e rastreada
como requisito do Projeto Odisseia, decisao da arquitetura tecnica, recurso observado no script
atual, inspiracao do Deepin/UOS AI ou nova proposta desta obra.

O objetivo pedagogico e deliberadamente ambicioso: conduzir uma pessoa com alguma experiencia
em Python, mas sem dominio de C, ate a compreensao, implementacao, compilacao, teste,
empacotamento e integracao de um agente nativo de sistema operacional. Os exemplos priorizam
contratos simples, privilegio minimo, diagnostico e degradacao graciosa em hardware limitado.

    1. A definição rigorosa da Atena
    A Atena é a plataforma de inteligência artificial do Athenas OS. Essa frase parece simples, mas
    impede o erro arquitetural mais perigoso do projeto: confundir o produto com o modelo que
    responde ao usuário. Um modelo de linguagem calcula probabilidades e gera tokens. A Atena
    organiza identidade, contexto, memória, conhecimento, ferramentas, permissões, interfaces,
    modelos e provedores para produzir uma experiência coerente de sistema operacional.

    Em termos de engenharia, o modelo é um componente substituível. Hoje a máquina pode usar um
    arquivo GGUF por meio do llama.cpp; amanhã pode usar Ollama, um endpoint compatível com a
    API da OpenAI, um serviço corporativo ou outro runtime ainda inexistente. A troca do motor
    cognitivo não deve apagar a personalidade pedagógica, o histórico autorizado, as políticas de
    privacidade, as Skills instaladas, o catálogo de ferramentas nem a integração com o Linux.

    Portanto, as seguintes equivalências são falsas:
●
      Atena não é um LLM.
●
      Atena não é llama.cpp.
●
      Atena não é Ollama.
●
      Atena não é uma janela de chatbot.
●
      Atena não é um shell com linguagem natural.
●
      Atena não é uma API comercial renomeada.

    A definição operacional correta é: Atena é um conjunto de serviços e interfaces que recebe
    uma intenção humana, reúne contexto permitido, escolhe capacidades adequadas,
    consulta um ou mais motores cognitivos, executa somente ferramentas autorizadas e
    devolve uma resposta rastreável.


      FONTE DO PROJETO                   O Projeto Odisseia descreve a Atena como socrática, híbrida e regional. Essas
      Requisito pedagógico               propriedades pertencem à plataforma e ao seu método, não aos pesos de um
      original                           modelo específico.



      PROPOSTA DO LIVRO                  A personalidade, o método socrático, as políticas e o contexto regional devem
      Contrato de                        residir em arquivos e serviços versionados do projeto. O prompt de um provider é
      identidade                         uma projeção temporária desse estado, nunca sua única cópia.



    O produto em uma frase
    Se o usuário remover todos os modelos, a Atena ainda deve conseguir abrir, mostrar configurações,
    gerenciar a base de conhecimento, explicar por que não pode responder e permitir a instalação de
    um novo motor. Se o usuário trocar de provider, a experiência permanece reconhecível. Se a rede
    cair, o sistema não desaparece. Esse comportamento distingue uma plataforma de um simples
    cliente de API.

2. O lugar da Atena no Projeto Odisseia
O Projeto Odisseia é um ecossistema educacional. O Cyberdeck Odisseia é a família de dispositivos
físicos. O Athenas OS é a distribuição Linux e a plataforma de software. Atena é a camada de
inteligência e mediação pedagógica. OdysseyOS permanece um nome histórico dos materiais iniciais
e não deve coexistir publicamente como se fosse sinônimo técnico de Athenas OS.

 Nome                                            Domínio                            Responsabilidade

 Projeto Odisseia                                Ecossistema                        Missão educacional, hardware, software
                                                                                    e comunidade

 Cyberdeck Odisseia                              Dispositivo                        Computador modular, reparável e
                                                                                    adaptado ao propósito

 Athenas OS                                      Distribuição Linux                 Base Debian, desktop, pacotes,
                                                                                    atualizações e integração

 Atena                                           Plataforma de IA                   Mentoria, agentes, modelos,
                                                                                    conhecimento, ferramentas e políticas

 OdysseyOS                                       Nome histórico                     Referência conceitual que deve ser
                                                                                    resolvida antes de um release público



Os materiais visuais do projeto associam o cyberdeck a autonomia, cultura maker,
reaproveitamento, identidade própria e compreensão do computador por dentro. Essa filosofia
influencia a Atena diretamente. Uma IA educacional coerente com o Odisseia não deve esconder
cada ação atrás de uma animação. Ela deve poder explicar qual provider foi escolhido, por que uma
ferramenta pediu confirmação, quais fontes sustentam uma resposta e quanto o modelo consumiu
da máquina.

O objetivo não é romantizar hardware antigo. Uma máquina com 2 GB de RAM não se torna
adequada a um LLM de bilhões de parâmetros por causa de uma boa intenção. O objetivo é
degradar com honestidade: oferecer busca lexical, documentação, diagnósticos e automações
tipadas quando inferência local pesada não for viável; permitir provider remoto somente com
consentimento; e preservar o funcionamento básico do Athenas OS sem IA.


     A pergunta do produto não é “qual modelo vamos instalar?”, mas “qual experiência
     continua útil, segura e explicável em cada classe de hardware?”.



O que este livro inclui e exclui
Este livro inclui tudo o que for necessário para compilar, instalar, executar, empacotar, atualizar e
integrar a Atena. Isso exige tratar de Debian, systemd, D-Bus, Polkit, PipeWire, pacotes .deb e
inclusão na ISO. Ele não ensina a construir uma distribuição Linux completa, desenhar um
bootloader ou reproduzir toda a configuração do desktop. Esses assuntos aparecem apenas nas
fronteiras em que a IA encontra o sistema.

5. Princípios de produto transformados em requisitos
Princípios só ajudam a engenharia quando produzem critérios verificáveis.

Local-first e offline-capable
Local-first significa que o caminho local é tratado como cidadão de primeira classe. Offline-capable
significa que funções essenciais continuam disponíveis sem rede. Isso não obriga todo hardware a
executar um LLM; obriga a Atena a oferecer um modo offline honesto, com documentação, RAG
lexical, ferramentas locais e UI funcional.

Cloud optional e provider-agnostic
Nenhuma API comercial pode ser requisito de instalação. O contrato de provider deve aceitar
implementações locais, remotas, corporativas e compatíveis com padrões conhecidos. Remover um
provider não pode corromper conversas, Skills ou memória.

Model-agnostic
Modelos anunciam capacidades, limites de contexto, formato, licença e requisitos. O Core solicita
uma capacidade; o Model Router escolhe um modelo adequado dentro do provider selecionado.
Nomes comerciais não aparecem espalhados pela lógica central.

Hardware-aware
Atena mede CPU, ISA, RAM disponível, swap, zram, GPU, VRAM, backend, armazenamento, energia
e temperatura quando disponível. Compatibilidade começa com estimativa e passa a usar
benchmark real da própria máquina.

Privacy-aware e permission-aware
Conteúdo privado não cruza a rede silenciosamente. Ferramentas não recebem privilégios
implícitos. Arquivos, diretórios e tipos de dado podem ter políticas próprias. Toda elevação
administrativa é realizada por componente pequeno, identificável e auditável.

Offline real
Rede indisponível ou bloqueada. Atena utiliza modelo local quando viável, RAG local, FTS5,
documentação e ferramentas locais. Providers remotos, pesquisa web, embeddings remotos, STT
remoto e TTS remoto ficam desabilitados. A UI mostra essa condição sem sugerir que uma operação
remota “falhou por acaso”.

Local conectado
O modelo permanece local, mas Search Provider e serviços autorizados podem usar rede. Prompts e
documentos continuam locais sempre que possível. O fato de um modelo executar localmente não
implica isolamento da internet; o acesso ocorre somente por ferramenta governada.

Cloud
O modelo principal está em endpoint remoto. A Atena ainda executa política, memória e
ferramentas localmente. Antes do envio, o Core reduz contexto, remove segredos e informa ao
usuário quando arquivos ou trechos serão transmitidos.

Híbrido
O router considera privacidade, capacidade, hardware, disponibilidade, latência, custo, qualidade e
preferência. Uma tarefa pode fazer recuperação local, consultar busca autorizada e sintetizar com
modelo local ou remoto. “Híbrido” não significa comportamento imprevisível: a decisão precisa ser
explicável e reproduzível a partir da política ativa.

    9. A Atena como mentora socrática
    O método socrático não é sinônimo de responder toda pergunta com outra pergunta. Em educação,
    a estratégia deve observar intenção, conhecimento prévio, urgência e risco. Se o estudante pede
    ajuda para entender um ponteiro, a Atena pode diagnosticar o modelo mental, propor uma analogia,
    pedir uma previsão sobre o código, executar um exemplo e corrigir a hipótese. Se o usuário pede
    um comando de recuperação urgente, perguntas excessivas atrapalham.

    O comportamento pedagógico deve ser um policy pack versionado. Um esboço de estados pode
    incluir:

1     identificar o objetivo do aprendiz;
2     estimar o nível com evidências da conversa atual;
3     recuperar conteúdo local e exemplos relevantes;
4     escolher entre explicação direta, pergunta guiada, demonstração ou exercício;
5     pedir ao estudante que antecipe o resultado;
6     fornecer feedback específico;
7     registrar progresso somente com autorização.

    Regionalidade sem estereótipo
    Identidade regional significa reconhecer contexto maranhense e brasileiro, idioma, exemplos,
    currículo e realidade de conectividade. Não significa forçar expressões locais em toda resposta nem
    reduzir uma cultura a decoração. O conteúdo regional deve ser fonte citável na base de
    conhecimento, revisado por educadores e separado do modelo.

12. A matemática mínima, construída por sentido
Um escalar é um único número, como a temperatura 0.7. Um vetor é uma lista ordenada de
números, como uma representação de 768 dimensões. Uma matriz organiza números em linhas e
colunas e pode representar uma transformação. Um tensor generaliza esse arranjo para mais
dimensões.

O significado não está em um número isolado. Ele emerge da posição relativa em um espaço
aprendido. Se dois trechos produzem vetores próximos segundo uma métrica, o sistema pode
tratá-los como semanticamente relacionados. Essa é a intuição dos embeddings usados no RAG
Standard.

Multiplicação matricial
Considere uma entrada x com características e uma matriz de pesos W. A expressão y = xW + b
mistura as características de x, aplica pesos e adiciona um viés b. Cada camada de uma rede repete
variações desse princípio. O formato das matrizes precisa ser compatível: a dimensão que sai de x
deve coincidir com a dimensão que entra em W.

Funções, probabilidade e softmax
Uma função recebe entrada e produz saída. O modelo gera logits, números ainda não
normalizados para cada token possível. Softmax transforma esses logits em uma distribuição de
probabilidade cuja soma é 1. A temperatura modifica o contraste dessa distribuição antes da
amostragem: valores menores concentram probabilidade nas opções dominantes; valores maiores
espalham escolhas.

Derivada e gradiente
Derivada mede como uma saída varia quando uma entrada muda. Gradiente é um vetor de
derivadas que aponta a direção de crescimento mais rápido de uma função. Durante treinamento, o
otimizador usa o gradiente da perda para ajustar os pesos em direção oposta, buscando reduzir o
erro.


     Treinar é encontrar pesos que reduzem uma medida de erro; inferir é usar pesos já
     encontrados para calcular uma saída.



13. Como uma rede neural aprende
Um neurônio artificial calcula uma soma ponderada de entradas, adiciona bias e aplica uma função
de ativação. O forward pass leva dados da entrada até a previsão. A função de perda compara
previsão e alvo. O backpropagation calcula como cada parâmetro contribuiu para o erro. O
otimizador atualiza os parâmetros.

 Conceito                                                     Explicação intuitiva

 peso                                                         intensidade e direção de uma conexão

 bias                                                         deslocamento que permite ativação mesmo com entradas
                                                              nulas

 ativação                                                     transformação não linear que amplia o que a rede pode
                                                              representar

 loss                                                         número que resume o erro do lote atual

 batch                                                        grupo de exemplos processados antes de uma atualização

 epoch                                                        passagem completa pelo conjunto de treino

 validação                                                    dados usados para medir generalização sem ajustar pesos

Memorizar o treino não basta. Um modelo que apresenta perda baixa em exemplos vistos e
desempenho ruim em dados novos sofreu overfitting. Separar treino, validação e teste ajuda a
detectar isso. Para a Atena, a mesma disciplina se aplica à avaliação de prompts, ferramentas e
roteamento: um conjunto de demonstrações não substitui testes fora da amostra.

14. Tokens, embeddings e Transformers
Texto precisa ser convertido em unidades numéricas. O tokenizer divide a entrada em tokens, que
podem corresponder a palavras, pedaços de palavra, sinais ou bytes. Cada token recebe um
identificador. Uma tabela de embeddings converte identificadores em vetores densos.

Transformers processam relações entre posições por atenção. Em uma forma simplificada, cada
posição produz vetores Q (query), K (key) e V (value). A similaridade entre Q e K determina quanto de
cada V contribui para a nova representação. A escala pela raiz da dimensão evita valores extremos
antes do softmax.

    TEXT

    Attention(Q, K, V) = softmax((Q x K^T) / sqrt(d_k)) x V



Self-attention significa que consultas, chaves e valores derivam da mesma sequência. Multi-head
attention executa projeções diferentes em paralelo, permitindo que relações distintas sejam
representadas. Uma camada também inclui bloco feed-forward, normalização e conexões residuais.
As residuais criam caminhos curtos para informação e gradiente; a normalização estabiliza escalas.

Informação de posição
A atenção pura não sabe que um token veio antes de outro. Informações posicionais são adicionadas
ou incorporadas ao cálculo. Implementações modernas usam diferentes técnicas, mas o princípio
permanece: a ordem precisa entrar no modelo.

Logits e geração autoregressiva
O modelo produz logits para o próximo token. Um método de amostragem escolhe um token,
anexa-o à sequência e repete o processo. O context window limita quantos tokens podem
participar. O KV cache guarda chaves e valores já calculados para evitar refazer toda a sequência a
cada token; por isso ele cresce com contexto, número de camadas e dimensões do modelo.


15. Quantização, contexto e custo real de inferência
Pesos treinados em alta precisão ocupam muito espaço. Quantização representa esses valores com
menos bits, reduzindo armazenamento e memória e frequentemente acelerando inferência. A
redução não é gratuita: diferentes esquemas alteram qualidade, velocidade e compatibilidade com
backends.

Uma estimativa grosseira do tamanho dos pesos é parâmetros x bits / 8. Um modelo de 2 bilhões
de parâmetros em 4 bits exigiria perto de 1 GB apenas para pesos, antes de metadados, buffers, KV
cache, runtime e sistema operacional. Portanto, “o arquivo cabe no disco” não significa “o modelo
cabe na RAM”.

O contexto também custa memória. Dobrar ctx-size pode aumentar muito o KV cache. Batch,
threads, GPU offload e tipo do cache mudam o perfil. Por isso o Model Manager exibe estimativa,
mas o Benchmark Engine registra o pico medido na máquina.

GGML e GGUF
GGML é a biblioteca/tensor engine que sustenta a família llama.cpp. GGUF é um formato de
arquivo extensível que armazena tensores e metadados necessários ao carregamento. O livro trata
GGUF como artefato de modelo, não como sinônimo de quantização: um GGUF pode conter
diferentes tipos de tensor e informações de arquitetura.

16. Usar, adaptar ou treinar
Usar um modelo significa executar inferência com pesos existentes. Adaptar significa especializar o
comportamento ou domínio. Fine-tuning atualiza parâmetros a partir de novos exemplos. LoRA
congela os pesos principais e aprende matrizes de baixa dimensão. QLoRA mantém a base
quantizada e treina adaptadores, reduzindo memória. Distillation treina um modelo aluno para
imitar sinais de um professor. Treinar do zero começa com pesos não especializados e exige dados,
computação, avaliação e operação em escala.

 Estratégia                          O que muda                Custo relativo   Uso inicial na Atena

 Prompt e política                   contexto enviado          baixo            obrigatório

 RAG                                 conhecimento recuperado   baixo a médio    obrigatório

 LoRA                                adaptadores               médio            experimento controlado

 QLoRA                               adaptadores sobre base    médio            laboratório com GPU
                                     quantizada                                 adequada

 Distillation                        novo aluno                alto             pesquisa futura

 Treino do zero                      todos os pesos            muito alto       não é estratégia inicial



O método socrático, a personalidade e o conhecimento regional não devem ser “enterrados”
imediatamente em fine-tuning. Arquivos versionados, RAG e políticas são mais fáceis de revisar,
atualizar e auditar. Fine-tuning passa a fazer sentido quando existe hipótese mensurável que
prompt e recuperação não resolvem.

  import json
  import math
  from pathlib import Path

  import torch
  import torch.nn as nn
  import torch.nn.functional as F

  TEXT = "atena ensina linux. linux revela o computador. " * 200
  chars = sorted(set(TEXT))
  stoi = {ch: i for i, ch in enumerate(chars)}
  itos = {i: ch for ch, i in stoi.items()}
  data = torch.tensor([stoi[ch] for ch in TEXT], dtype=torch.long)

  BLOCK = 48
  BATCH = 16

  def batch():
      starts = torch.randint(0, len(data) - BLOCK - 1, (BATCH,))
      x = torch.stack([data[i:i + BLOCK] for i in starts])
      y = torch.stack([data[i + 1:i + BLOCK + 1] for i in starts])
      return x, y

  class Head(nn.Module):
      def __init__(self, width, head_size):
          super().__init__()
          self.key = nn.Linear(width, head_size, bias=False)
          self.query = nn.Linear(width, head_size, bias=False)
          self.value = nn.Linear(width, head_size, bias=False)
          self.register_buffer("mask", torch.tril(torch.ones(BLOCK, BLOCK)))

      def forward(self, x):
          _, t, _ = x.shape
          k, q, v = self.key(x), self.query(x), self.value(x)
          scores = q @ k.transpose(-2, -1) / math.sqrt(k.size(-1))
          scores = scores.masked_fill(self.mask[:t, :t] == 0, float("-inf"))
          return F.softmax(scores, dim=-1) @ v

  class TinyTransformer(nn.Module):
      def __init__(self, vocab, width=64):
          super().__init__()
          self.token = nn.Embedding(vocab, width)
          self.pos = nn.Embedding(BLOCK, width)
          self.head = Head(width, width)
          self.ff = nn.Sequential(
              nn.Linear(width, 4 * width), nn.ReLU(), nn.Linear(4 * width, width)
          )
          self.norm1, self.norm2 = nn.LayerNorm(width), nn.LayerNorm(width)
          self.out = nn.Linear(width, vocab)

      def forward(self, ids, targets=None):
          _, t = ids.shape
          x = self.token(ids) + self.pos(torch.arange(t, device=ids.device))
          x = x + self.head(self.norm1(x))
          x = x + self.ff(self.norm2(x))
          logits = self.out(x)
          loss = None
          if targets is not None:
              loss = F.cross_entropy(logits.view(-1, logits.size(-1)), targets.view(-1))
          return logits, loss

  model = TinyTransformer(len(chars))
  optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)

  for step in range(1500):
      x, y = batch()
      _, loss = model(x, y)
      optimizer.zero_grad(set_to_none=True)
      loss.backward()
      optimizer.step()
      if step % 150 == 0:
          print(step, float(loss))

  torch.save(model.state_dict(), "tiny-atena.pt")
  Path("tiny-atena-vocab.json").write_text(json.dumps(stoi), encoding="utf-8")

19. Código-fonte, compilador e programa
Código-fonte é texto escrito em uma linguagem. O processador não executa diretamente if, struct
ou nomes de função; ele executa instruções da arquitetura da CPU. O compilador analisa o código,
verifica tipos, transforma-o em representação intermediária, otimiza e produz código de máquina. O
linker, ou ligador, combina objetos e bibliotecas para formar o executável.

No Debian, GCC e Clang são duas cadeias de compilação importantes. O projeto deve funcionar com
ambas sempre que possível. Começaremos com comandos explícitos para entender as etapas;
depois adotaremos CMake para builds reproduzíveis.

      C

      #include <stdio.h>

      int main(void) {
          puts("Atena Core iniciando");
          return 0;
      }



      BASH

      cc -std=c17 -Wall -Wextra -Wpedantic -Werror \
         hello.c -o hello
      ./hello



-std=c17 seleciona a versão da linguagem. -Wall -Wextra -Wpedantic ativa avisos. -Werror
transforma aviso em erro durante integração contínua. Um aviso não é “apenas estética”:
frequentemente revela conversão perigosa, retorno ignorado ou variável sem uso.

As quatro etapas visíveis
      BASH

      cc -E hello.c -o hello.i           # pre-processamento
      cc -S hello.i -o hello.s           # assembly
      cc -c hello.s -o hello.o           # objeto
      cc hello.o -o hello                # link



O pre-processador expande #include e macros. O compilador produz assembly. O assembler cria o
arquivo objeto. O linker resolve símbolos como puts. Entender essa cadeia ajuda a diagnosticar
“header não encontrado”, “undefined reference” e incompatibilidade de arquitetura.

tamanho de int não deve ser presumido para formatos persistentes. Use tipos de largura definida
de <stdint.h> quando o protocolo exige uint32_t, int64_t e semelhantes.

Conversões e overflow
Converter um número maior para um tipo menor pode truncar bits. Inteiro sem sinal faz aritmética
modular; overflow de inteiro com sinal é comportamento indefinido. O hardware profiler lida com
bytes e contadores grandes, então deve validar limites antes de somar ou multiplicar.

22. Funções, contratos e erros
Função encapsula uma transformação ou efeito. Um bom contrato declara pré-condições, resultado
e erros. Em C não há exceções nativas; APIs normalmente usam retorno, parâmetros de saída e
códigos de erro.

      C

      typedef enum {

errno
Funções POSIX podem sinalizar detalhes em errno. Ele só é significativo quando a função
documenta falha. Leia-o imediatamente e converta a mensagem para uma estrutura própria. Não
use errno como estado global do Core.

Strings C são arrays de char terminados por byte zero. O terminador ocupa espaço. Funções que
não conhecem a capacidade do destino são fonte recorrente de vulnerabilidades.

25. Ponteiros sem misticismo
Ponteiro contém um endereço de memória. &value obtém o endereço; *pointer acessa o objeto
apontado. O tipo informa como interpretar os bytes e quanto avançar em aritmética de ponteiros.

      C

      void clamp_temperature(double *value, double low, double high) {
          if (value == NULL) return;
          if (*value < low) *value = low;
          if (*value > high) *value = high;
      }



O ponteiro não carrega validade automática. Pode ser nulo, apontar para objeto já liberado, ter
alinhamento errado ou referir menos bytes do que a função espera. O contrato de ownership
responde: quem cria? quem pode modificar? quem libera? por quanto tempo o endereço permanece
válido?

26. Stack, heap, malloc e ciclo de vida
A stack guarda frames de chamadas, parâmetros e variáveis automáticas. Sua liberação ocorre
quando a função retorna. O heap guarda alocações com ciclo de vida explícito. malloc reserva bytes
sem inicializar; calloc inicializa com zero; realloc tenta redimensionar; free libera.

  typedef struct {
      char *data;
      size_t length;
      size_t capacity;
  } AtenaBuffer;

  AtenaStatus buffer_init(AtenaBuffer *b, size_t initial) {
      if (b == NULL || initial == 0) return ATENA_ERR_INVALID;
      b->data = malloc(initial);
      if (b->data == NULL) return ATENA_ERR_NOMEM;
      b->data[0] = '\0';
      b->length = 0;
      b->capacity = initial;

  void buffer_deinit(AtenaBuffer *b) {
      if (b == NULL) return;
      free(b->data);
      b->data = NULL;
      b->length = 0;
      b->capacity = 0;
  }



Erros clássicos incluem leak (esquecer free), use-after-free, double free, acesso além do limite e

simplifica revisão.

realloc seguro
Não atribua realloc diretamente ao ponteiro original. Em falha, ele retorna NULL e a alocação
anterior continua válida; uma atribuição direta perderia o endereço.

Cada chamada guarda endereço de retorno e estado necessário. Recursão profunda consome stack.
O chunker de documentos deve preferir iteração em arquivos enormes; um parser recursivo precisa
de limites explícitos para entrada não confiável.

contrato. Dependências apontando em todas as direções produzem builds frágeis e testes difíceis.

e libcurl são opções disponíveis no ecossistema Debian.

31. Processos, threads, sinais e IPC
Processo possui espaço de endereçamento isolado. Thread compartilha memória dentro do
processo. Concorrência melhora responsividade, mas cria condições de corrida quando múltiplas
threads acessam estado mutável sem coordenação.

O Core pode usar um event loop para sockets e tarefas curtas, com pool limitado para extração e
chamadas bloqueantes. Inferência local pesada ocorre no llama-server ou runtime dedicado, não
em uma thread que congela a UI.

Cancelamento
Cancelar é parte do contrato. A UI emite cancelamento pelo ID; o Core marca o request; provider
interrompe streaming; Tool Engine decide se a ação já iniciada pode ser revertida. SIGKILL é último
recurso porque não permite limpeza.

Socket Unix
No estágio inicial de serviço, um socket em $XDG_RUNTIME_DIR/atena/core.sock oferece IPC local.
O diretório já é associado ao usuário e à sessão. O servidor valida credenciais do peer, limita
mensagem e usa framing explícito, como comprimento de 32 bits seguido de JSON. “Uma linha por
JSON” serve ao protótipo, mas strings podem conter quebras e mensagens enormes exigem limite.

D-Bus
D-Bus é adequado para APIs de desktop e descoberta de serviços. Métodos devem ser semânticos,
não ExecuteShell(string). Exemplos: Ask, Cancel, ListModels, InvokeSkill. Sinais transportam
tokens parciais e mudança de estado. Dados volumosos, como áudio e arquivos, usam descritores ou
caminhos autorizados, não blocos ilimitados no barramento.

35. Desenvolvimento vertical e contratos primeiro
O Core será construído por fatias verticais. A primeira fatia recebe texto na CLI, forma um
AtenaRequest, escolhe um provider simulado, transmite tokens e registra resultado. A segunda
substitui o provider simulado por llama-server. A terceira acrescenta política e uma ferramenta
segura. Cada fatia compila, testa e produz comportamento observável.

Antes da implementação, criamos contratos independentes de provider:

Eventos unificam streaming local e remoto. O payload de cada tipo possui schema. A UI não precisa

Imutabilidade lógica
Depois de entrar no Request Engine, campos de segurança do request não são alterados por
provider ou agente. Uma tarefa derivada cria novo objeto com relação explícita ao pai. Isso impede
que uma Skill mude privacy=PRIVATE para NORMAL no mesmo ponteiro.


36. Request Engine e Context Builder
O Request Engine valida tamanho, UTF-8, session ID, origem e anexos. Em seguida, classifica a
tarefa e cria um plano de contexto. O Context Builder reúne apenas o necessário: instruções da
Atena, estado de sessão, trechos RAG, resultados de ferramentas e histórico dentro do orçamento
de tokens.

O contexto é uma montagem temporária. Banco de memória e documentos não são copiados
integralmente para o prompt. Cada fragmento registra origem e classe de privacidade.

43. Agent Engine
Agente é um ciclo que observa estado, escolhe uma ação, recebe resultado e decide se terminou. O
LLM propõe; a plataforma governa. Um limite de passos evita loops. Um orçamento limita tokens,
tempo e custo. O plano é apresentado antes de tarefas longas ou de alto risco.

    TEXT

    request -> task -> plan -> next action -> policy -> tool
            -> observation -> update plan -> answer or next action



Estados mínimos: PLANNING, WAITING_CONFIRMATION, RUNNING_TOOL, OBSERVING, COMPLETED,
CANCELLED, FAILED. Persistir estado permite recuperar UI sem repetir efeitos.

Workflow versus agente
Workflow conhece etapas. Agente escolhe dinamicamente. “Indexar este PDF” é workflow
determinístico. “Prepare o ambiente para compilar este projeto” pode exigir agente, mas cada ação
ainda usa tools. Prefira workflow quando a sequência é conhecida: é mais testável e previsível.

Multi-agent
Vários agentes acrescentam coordenação, estado e risco. Não são necessários ao MVP. Quando
adotados, cada agente recebe capabilities mínimas e o coordenador continua sob Policy Engine
comum. “Especialista em segurança” não ganha rede ou root por causa do nome.

    Rate limit é tratado como estado temporário com retry-after, fila limitada e fallback autorizado.

59. RAG: recuperação antes de geração

   Pipeline da base de conhecimento




                                                                                                     Resposta
        Documento           Extractor           Chunker       Metadata     Index   Retrieval
                                                                                                      citada




RAG adiciona memória não paramétrica. O pipeline ingere documento, extrai texto, divide em
chunks, associa metadados, indexa, recupera e entrega evidências ao modelo. Uma resposta
confiável preserva documento, página, trecho, arquivo ou URL.

Ingestão
O extractor detecta MIME por conteúdo, não só extensão. PDF textual usa biblioteca de extração;
PDF escaneado requer OCR opcional e marca confiança. Código preserva arquivo e linhas.
Markdown preserva headings. Arquivos protegidos ou grandes exigem consentimento e limite.

Chunking
Chunks não devem cortar qualquer quantidade fixa de caracteres. Estratégia hierárquica usa
seções, parágrafos e tamanho máximo em tokens, com pequena sobreposição. Cada chunk mantém
document_id, página/linha, heading, hash e privacy class.

    {
        "chunk_id": "sha256:...#p21-c03",
        "document_id": "project-architecture",
        "source_name": "Projeto_Odisseia_Athenas_OS_Arquitetura_Tecnica.pdf",

61. RAG Standard e Advanced
RAG Standard adiciona embeddings locais. Um modelo de embedding transforma consulta e chunks
em vetores. Similaridade por cosseno recupera sem depender de palavras idênticas. O modelo de
embedding é separado do gerador e aparece no Model Manager com licença, dimensão e
benchmark.

RAG Advanced combina busca lexical e vetorial, funde rankings e aplica reranker local quando
hardware permite.

    TEXT

    lexical candidates ----+
                           +-> reciprocal rank fusion -> reranker -> top evidence
    vector candidates -----+



Reciprocal Rank Fusion combina posições sem exigir scores na mesma escala. Reranking melhora
ordem, mas acrescenta latência. O perfil LIGHT pode usar apenas FTS5; STANDARD usa híbrido
sem reranker; ADVANCED habilita o pipeline completo.

Avaliação
Crie perguntas com documentos e locators esperados. Meça Recall@k, precisão, MRR e cobertura
de citação. Em seguida, avalie se a resposta usa somente evidências. Um retrieval excelente ainda
pode ser mal sintetizado; as duas fases têm testes separados.

62. Citation Engine
Citação não é um link decorativo. Cada trecho de evidência recebe ID e locator. O modelo emite
referências estruturadas, que o Core valida. Se uma referência não pertence ao conjunto
recuperado, é rejeitada.

    JSON

    {
        "answer_blocks": [
           {
             "text": "A Atena foi definida como socratica, hibrida e regional.",
             "citations": ["evidence-2"]
           }
        ],
        "evidence": {
           "evidence-2": {
             "document": "Projeto Odisseia.pdf",
             "page": 8,
             "locator": "p8"
           }
        }
    }



Para URL, guarde URL canônica, título, data de acesso e data do conteúdo quando conhecida. Para
código, arquivo, commit e intervalo de linhas. Para PDF, página impressa e índice interno podem
diferir; a UI mostra ambos quando necessário.

Resposta insuficiente
Se a evidência não sustenta a afirmação, a Atena deve dizer que não encontrou base. RAG não
transforma qualquer resultado em verdade. Uma opção “somente fontes” proíbe conhecimento
externo do modelo para tarefas de auditoria.

   Fluxo de voz opcional




       Microfone            PipeWire              STT         Atena Core   LLM / Tool   TTS           Alto-falante




Voz é uma interface, não um caminho privilegiado. A transcrição vira request comum; tools seguem
a mesma política. A resposta textual pode ser sintetizada por TTS. O usuário pode cancelar falando,
pressionando tecla ou clicando.

Captura com PipeWire
PipeWire fornece captura e reprodução com modelo de segurança apropriado ao desktop. A
primeira implementação pode usar pw-record/biblioteca de alto nível; a versão nativa usa
pw_stream. A UI mostra indicador de microfone e dispositivo ativo.

STT
Opções locais devem ser avaliadas por idioma e hardware. whisper.cpp oferece caminho C/C++;
Vosk possui modelos pequenos e português; serviços remotos são fallback opcional. O Provider
Manager trata STT como capability, com latência, memória, licença e rede.

TTS
Piper é referência de TTS local rápido, mas versão, licença e API precisam ser verificadas no
empacotamento. Speech Dispatcher pode integrar acessibilidade. Vozes são modelos separados com
idioma, licença, tamanho e amostras.

Wake word
Wake word é futura e desabilitada por padrão. Escuta contínua afeta privacidade, bateria e falsos
positivos. O detector local não transmite áudio; a UI fornece chave física/lógica para desligar. Buffer
atrasado é curto, volátil e documentado.

Streaming e interrupção
STT parcial pode atualizar a UI sem disparar ação até confirmação de final de fala. TTS começa por
sentenças, mas interrompe imediatamente quando usuário cancela. Echo cancellation evita que a
própria voz da Atena volte ao microfone.

  typedef struct {

      bool fail_after_first_chunk;

  static AtenaStatus mock_generate(
      AtenaProvider *self,
      const AtenaRequest *request,
      AtenaStreamSink *sink
  ) {
      if (self == NULL || request == NULL || sink == NULL) {
          return ATENA_ERR_INVALID;
      }

      const char *chunks[] = {
          "Atena recebeu: ",
          request->user_text,
          "\nResposta gerada pelo provider de teste."
      };

      MockState *state = self->impl;
      for (size_t i = 0; i < 3; ++i) {
          AtenaEvent event = {
              .type = ATENA_EVENT_TEXT_DELTA,
              .request_id = request->id,
              .json_payload = chunks[i]
          };
          AtenaStatus status = sink->emit(sink, &event);
          if (status != ATENA_OK) return status;
          if (state->fail_after_first_chunk && i == 0) {
              return ATENA_ERR_PROVIDER;
          }
      }
      return sink->done(sink, request->id);
  }



O teste simula erro após chunk, cancelamento e sink que recusa escrita. A UI precisa terminar

82. Router determinístico inicial
    C

    AtenaStatus select_provider(
        const AtenaRequest *request,
        const AtenaProviderInfo *providers,
        size_t count,
        size_t *selected
    ) {
        if (request == NULL || providers == NULL || selected == NULL) {
            return ATENA_ERR_INVALID;
        }

         double best = -1.0;
         size_t best_index = 0;
         bool found = false;

         for (size_t i = 0; i < count; ++i) {
             const AtenaProviderInfo *p = &providers[i];
             if (!p->is_available) continue;
             if ((p->capabilities & request->required_capabilities)
                     != request->required_capabilities) continue;
             if (!request->allow_network && !p->is_local) continue;
             if ((request->privacy == ATENA_PRIVACY_PRIVATE ||
                  request->privacy == ATENA_PRIVACY_SECRET) && !p->is_local) continue;

              double score = p->is_local ? 10.0 : 5.0;
              score += p->health_score;
              score += p->quality_score;
              score -= p->estimated_cost_score;

              if (!found || score > best) {
                  found = true;
                  best = score;
                  best_index = i;
              }
         }

         if (!found) return ATENA_ERR_UNSUPPORTED;
         *selected = best_index;
         return ATENA_OK;
    }



Produção também retorna justificativas. Este código demonstra a ordem: filtros de segurança antes
do score.

    95. Conclusão
    Atena nasce da combinação entre autonomia técnica e responsabilidade. A plataforma pode operar
    offline, usar nuvem opcional, escolher modelos conforme hardware, pesquisar com autorização,
    citar documentos, falar, ouvir, ensinar e executar ferramentas. Nenhuma dessas capacidades
    precisa depender de um único fornecedor. Nenhuma exige entregar root ao modelo.

    O desenho final preserva cinco separações: plataforma versus modelo; provider versus model;
    conhecimento versus memória; intenção versus efeito; usuário versus privilégio administrativo.
    Essas fronteiras permitem evolução sem reescrever tudo e segurança sem transformar o
    computador educacional em uma caixa fechada.

    Para o Projeto Odisseia, isso possui sentido maior: o cyberdeck não é apenas um objeto futurista e a
    Atena não é apenas uma conversa convincente. Ambos são meios para que o estudante compreenda
    a máquina, questione decisões, teste hipóteses e construa tecnologia própria. A meta não é
    esconder complexidade, mas organizá-la até que possa ser aprendida.
